# Нагрузочное тестирование API в JMeter — домашнее задание 3

**[Отчёт с результатами](report/report.md)** · **[Сценарий JMeter (.jmx)](load/task-lifecycle.jmx)** · [CSV-данные](load/users.csv)

Учебный API задач: Spring Boot MVC, JDBC, H2 и Actuator. Сценарий JMeter выполняет полный цикл работы с задачей и проверяет сохранение данных. Проект независим от предыдущих заданий.

## Запустить API

Требуются **JDK 17+**, Maven 3.6.3+. При первой сборке Maven скачивает зависимости.

```sh
mvn verify
java -Xms256m -Xmx512m -jar target/jmeter-api-lab-1.0.0.jar
```

Приложение доступно только локально, на `http://127.0.0.1:8084`. H2 работает в памяти; при каждом запуске создаются 200 исходных задач. Настройка внешней БД не нужна. Пул соединений Hikari — 10, остальные параметры Tomcat — стандартные для указанной версии Spring Boot. Четыре HTTP-теста проверяют CRUD, фильтрацию, страницы, валидацию и отсутствие записи.

```sh
curl 'http://127.0.0.1:8084/actuator/health'
curl 'http://127.0.0.1:8084/api/tasks?status=OPEN&minPriority=3&q=study&limit=10&offset=0'
curl -i -X POST 'http://127.0.0.1:8084/api/tasks' \
  -H 'Content-Type: application/json' -d '{"title":"Prepare report","priority":3}'
```

POST вернёт HTTP 201, созданную задачу и заголовок Location. Подставьте полученный `id` вместо `201`:

```sh
curl 'http://127.0.0.1:8084/api/tasks/201'
curl -X PUT 'http://127.0.0.1:8084/api/tasks/201' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Report finished","priority":5,"status":"DONE"}'
curl -i -X DELETE 'http://127.0.0.1:8084/api/tasks/201'
```

GET и PUT: 200, DELETE: 204, неизвестный ID: 404, неверные параметры: 400. Заголовок задачи — 1–120 символов, priority — 1–5, status — OPEN/DONE, limit — 1–100, offset — неотрицательный. Поиск подстроки `q` регистронезависимый, список отсортирован по id.

## Открыть сценарий в JMeter

Использован **Apache JMeter 5.6.3** с JDK 17. Скачайте его с [официального сайта](https://jmeter.apache.org/download_jmeter.cgi), распакуйте и откройте `load/task-lifecycle.jmx` через File → Open. Сохраняйте `users.csv` рядом с `.jmx`: это единственный внешний файл, необходимый сценарию. Groovy-проверки встроены в `.jmx`; [validate.groovy](load/validate.groovy) — их читаемая копия, а не отдельная исполняемая зависимость.

Thread Group по умолчанию: **10 пользователей, ramp-up 10 секунд, длительность 45 секунд**. Uniform Random Timer добавляет 200–600 мс перед каждым запросом. Это ускоренная модель работы пользователей. HTTP Keep-Alive включён, тайм-аут подключения 3 с, ответа 10 с. При ошибке проверок пользователь останавливается, чтобы не создавать каскад неверных запросов.

Каждая итерация:

1. GET списка с фильтрами и пагинацией из CSV/переменных.
2. POST задачи с уникальным UUID в заголовке.
3. GET созданной задачи по ID, извлечённому из POST.
4. PUT изменяет заголовок, приоритет и статус на DONE.
5. GET повторно проверяет сохранённые изменения.
6. DELETE удаляет свою тестовую задачу.

Проверяются точные HTTP-коды, JSON, id, заголовок, приоритет, статус, фильтрация и порядок элементов. Каждый пользователь использует собственный ID. Список допустимо получить пустым, но ответ всё равно должен иметь правильную структуру.

## Нагрузка через командную строку

Для измерений используйте CLI, а GUI — для просмотра/отладки. Запуск через JAR поддерживает пути с пробелами:

```sh
java -Xms256m -Xmx512m -Djava.awt.headless=true \
  -jar /path/to/apache-jmeter-5.6.3/bin/ApacheJMeter.jar \
  -n -t load/task-lifecycle.jmx -Jusers=50 -Jramp=10 -Jduration=45 \
  -Jdata=/absolute/path/to/load/users.csv \
  -Jjmeter.save.saveservice.assertion_results_failure_message=true \
  -Jjmeter.reportgenerator.overall_granularity=5000 \
  -l requests.jtl -e -o dashboard
```

Каталоги результатов должны быть новыми. Дополнительные свойства: `-Jhost=127.0.0.1`, `-Jport=8084`, `-Jthink=200`, `-Jjitter=400`. Таймер равен `think + случайное число от 0 до jitter` мс. Не направляйте сценарий записи на чужой сервис: он предназначен для локального API этого проекта.

## Повторить весь эксперимент

Нужен также Python 3.9+. Сначала соберите JAR и остановите вручную запущенный API: скрипт сам запускает и завершает свой экземпляр.

```sh
python3 scripts/run_load.py \
  --java-home /absolute/path/to/jdk17 \
  --jmeter /absolute/path/to/apache-jmeter-5.6.3/bin/ApacheJMeter.jar \
  --output results-new
```

Скрипт проверен на macOS; также рассчитан на Linux. На Windows Java и JMeter работают, но для запуска этого Python-скрипта надо адаптировать имена утилит к `.exe`.

Последовательность: отрицательная проверка с priority=0; прогрев 10 пользователей/20 с; четыре фазы по 45 с — 10, 50, 150, снова 10 пользователей. Между фазами скрипт удаляет оставшиеся `load-...` задачи, проверяет работоспособность, делает паузу 3 с. Остатки появляются, если расписание JMeter завершило пользователя посреди цикла; они учитываются отдельно. Эти служебные DELETE и опросы Actuator не входят в JTL нагрузочного сценария.

Одновременно собираются CPU, heap, число JVM-потоков и состояние пула Hikari через Actuator. Перед пиком jcmd запускает 55-секундную запись JFR (`settings=profile`), сохраняемую локально в `peak.jfr`. Для её просмотра подходят JDK Mission Control или команда `jfr summary peak.jfr`. Сырые JFR исключены из Git; вывод анализа сохранён в результатах.

Для повторного экспорта JFR выполните `python3 scripts/profile_summary.py --java-home /path/to/jdk17 --results results-new`. Скрипт сохраняет сводку, сжатый JSON исходных событий и агрегат выборок стека. 55-секундная запись захватывает пик и короткий переход после него.

После опыта скрипт проверяет отсутствие ошибок основных фаз и восстановление исходных 200 задач. Код завершения JMeter сам по себе не доказывает успешность запросов: скрипт отдельно читает поле `success` в JTL.

## Результаты и анализ

В `results` сохранены оригинальные JTL, вывод JMeter, снимки Actuator, статистика и архивы HTML Dashboard. Распакуйте `dashboard.zip` нужной фазы и откройте `index.html` в браузере. Для просмотра JTL в GUI можно загрузить его в Aggregate Report. Намеренная ошибка в `validation-check` отделена от основных фаз.

Для пересчёта статистики и графика нужен Matplotlib 3.9.4:

```sh
python3 -m venv .tools/analysis-env
.tools/analysis-env/bin/pip install matplotlib==3.9.4
.tools/analysis-env/bin/python scripts/analyze.py --results results
```

Анализатор отдельно считает весь запуск и общее для всех фаз окно **15–40 секунд от первого HTTP-запроса**. Для окна отбираются завершённые в нём запросы, throughput = count / 25 с. p95 и p99 рассчитываются методом nearest rank; они могут слегка отличаться от интерполяции в HTML Dashboard JMeter. Длительность `elapsed` в JTL имеет разрешение в миллисекундах, поэтому нулевой результат не означает отсутствие затрат времени.

В `summary.json` находятся общие показатели, в `endpoints.csv` — показатели шести операций. Паузы пользователя не входят во время отдельного запроса, но ограничивают общую интенсивность сценария. Модель замкнутая: при замедлении сервиса пользователь отправляет меньше запросов. Это не поиск максимальной пропускной способности и не длительный soak-тест.

В личный кабинет нужно самостоятельно прикрепить публичную ссылку на [отчёт](report/report.md).
